ERRO DE INICIALIZAÇÃO CORRIGIDO
Erro observado no Streamlit Cloud:
Catalog Error: Table with name "transactions" already exists!

CAUSA IDENTIFICADA
A primeira abertura do app pode provocar reruns ou sessões concorrentes enquanto a base da PBH ainda está sendo construída. A versão anterior usava sempre o mesmo banco temporário, itbi_bh.tmp.duckdb. Duas execuções simultâneas podiam abrir o mesmo arquivo e tentar criar a tabela transactions, gerando a colisão exibida na tela.

CORREÇÃO IMPLEMENTADA
1. Lock exclusivo de atualização em arquivo para serializar cargas concorrentes entre sessões/reruns.
2. Banco temporário exclusivo por build, com UUID no nome; duas cargas nunca compartilham o mesmo arquivo temporário.
3. A segunda sessão aguarda a primeira. Depois do lock, confere novamente a base e reaproveita a carga concluída, sem reconstruí-la desnecessariamente.
4. Locks órfãos antigos são detectados e removidos após limite de segurança.
5. Builds que falham limpam banco temporário e WAL residual.
6. Se uma espera excepcionalmente longa esgotar o limite, a interface informa que outra sessão está preparando a base, em vez de exibir um erro técnico bruto.
7. Atualização manual forçada continua reconstruindo a base quando o usuário solicita explicitamente.

TESTES NOVOS DE REGRESSÃO
- Duas sessões competindo pelo lock nunca entram simultaneamente na seção crítica.
- Lock órfão antigo é substituído com segurança.
- Timeout do lock gera exceção específica e tratável pela interface.
- Segunda atualização concorrente reaproveita a base criada pela primeira; apenas um build é executado.
- Atualização forçada não reutiliza silenciosamente a base existente.
- Build inválido remove banco temporário e WAL residual.
- Teste de integração com DuckDB real e CSV de 1.000 registros executa duas atualizações iniciais concorrentes: ambas concluem com 1.000 registros, há apenas uma tabela transactions, nenhum arquivo de build fica residual e o erro "table already exists" não ocorre.

CORREÇÃO ADICIONAL — ROLAGEM EM AVALIAÇÕES CONSECUTIVAS
Relato reproduzido funcionalmente pelo estado da aplicação: a primeira avaliação solicitava rolagem, mas a segunda reutilizava a mesma posição do elemento st.html na árvore do Streamlit. A versão anterior alterava token e id do marcador, porém continuava emitindo o JavaScript no mesmo slot de renderização. Os testes anteriores verificavam a troca do token e do marcador, mas não verificavam que o navegador recebia o script em uma nova posição de montagem.

NOVA ESTRATÉGIA
1. Cada cálculo continua recebendo token crescente.
2. O marcador de resultado continua único por cálculo.
3. Para o token N, o app emite N-1 elementos HTML inertes e monta o script de rolagem no N-ésimo slot.
4. Assim, o script da avaliação seguinte não apenas muda de conteúdo: ele nasce em uma nova posição da árvore do Streamlit.
5. O script tenta localizar o marcador durante até 4 segundos e faz uma correção final de posição após 650 ms, para acomodar alterações de layout durante a animação.
6. Reruns normais sem novo cálculo não montam script de rolagem.

TESTES NOVOS DE REGRESSÃO DA ROLAGEM
- Primeira avaliação: exatamente 1 elemento HTML de rolagem, com JavaScript apontando para hybrid-result-anchor-1.
- Segunda avaliação consecutiva: primeiro slot inerte + novo script no segundo slot, apontando para hybrid-result-anchor-2.
- Terceira avaliação consecutiva: dois slots inertes + novo script no terceiro slot, apontando para hybrid-result-anchor-3.
- Rerun normal após resultado: nenhum script de rolagem é remontado.
- Mudança Avaliar → Mercado → Avaliar: não provoca nova rolagem sem cálculo.
- Sequência de avaliação por imóvel selecionado seguida de avaliação manual: token avança e o segundo script nasce em novo slot.
